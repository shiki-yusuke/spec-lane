# Spec — R46 vendored reason catalog (closes the I-2026-08-18 contract_boundary gap)

## Intent summary

`evaluateReview()` (packages/core/src/design-independence.ts) computes why one critic review does or
does not qualify as independent verification of a design-options document (R16-R23,
I-2026-08-18-design-critic-injection). Its `reasons` are meant to satisfy R46: "Reason text ... SHALL
be composed from whole catalogued messages ... and SHALL NOT be assembled by concatenating sentence
fragments." Until now, part of that text came verbatim from the vendored
`packages/core/src/vendor/derive-independence/v1/derive-independence.mjs` module, whose strings carry
no catalog identifier at all — `ReviewEvaluation.reasons` stayed a plain `string[]`, deliberately not
branded `CatalogBackedDesignMessage[]`, because doing so by assertion would have stated a guarantee
that was false.

Upstream (`ai-agent-skills-playbook`) closed the underlying gap in PR #15
(`feat/derive-independence-structured-reasons`, merged as `36df11adfb361873abbc04ec864aa5a36f8e9d7e`):
every reason the module emits is now additionally a `{code, params}` record (`reason_records`, a
closed 20-value `REASON_CODES` set, `formatReasonRecord` for the unchanged-wording projection). This
spec re-vendors that commit and wires the new `reason_records` through lane's own catalog
(`design-messages.ts`), so `ReviewEvaluation.reasons` becomes fully `CatalogBackedDesignMessage[]`.

## Premise

Recorded in `intent.yaml` (`method: code-only`). Two facts, both directly read rather than assumed:

1. The gap being closed is real and already on record:
   `docs/spec/I-2026-08-18-design-critic-injection/verification.yaml`'s `test_gaps` has a
   `taxonomy: contract_boundary` entry stating exactly this — `ReviewEvaluation.reasons` stays plain
   `string[]` because the vendored implementation's strings carry no catalog identifier, and closing
   it "needs upstream to return structured `{code, params}` reasons and a re-vendor."
2. Upstream now provides that: `ai-agent-skills-playbook`'s `main` at
   `36df11adfb361873abbc04ec864aa5a36f8e9d7e` (`contracts/shared/derive-independence.mjs`) exports
   `REASON_CODES`, `formatReasonRecord` (throws on an unrecognized code), and every derivation
   function now returns an additive `reason_records: {code, params}[]` field. Confirmed by reading
   the file directly at that commit, not by trusting the PR description alone.

## Scope

**In scope**: re-vendoring `derive-independence.mjs` (+ its hand-written `.d.mts`), updating the
`UPSTREAM` pin and `pin-verify.test.ts`'s hardcoded pin constants, adding the vendored-code → catalog
entry mapping in `design-independence.ts`, adding the new catalog entries this mapping needs, and the
tests that hold both exhaustive.

**Out of scope**: `packages/schemas` (no schema in this repo needed to change; the frozen
`estimate/v2` contract is untouched — separate concern entirely), any change to what `lane design
status`/gate *decide* (derived_status, qualifying, coverage, establishment) — only how the *reasons
behind* those decisions are rendered. `packages/core/dist/vendor/derive-independence` is build output
regenerated by `pnpm run build`, not edited directly.

## EARS Rules

- **R1** WHEN `evaluateReview()` builds a review's `reasons`, EACH element SHALL be a
  `CatalogBackedDesignMessage` produced by filling a catalog template — never a raw string copied from
  the vendored module, and never a string built by concatenation.
- **R2** The vendored `derive-independence.mjs` SHALL be re-vendored byte-for-byte from
  `ai-agent-skills-playbook` `main` commit `36df11adfb361873abbc04ec864aa5a36f8e9d7e`, and
  `packages/core/src/vendor/derive-independence/UPSTREAM`'s recorded commit and content hash SHALL
  match the vendored bytes exactly (verified by the existing, always-run
  `upstream-markers.test.ts`/`pin-verify.ts` content check).
- **R3** `mapReasonRecordToDesignMessage` SHALL handle every code in the vendored module's own
  `REASON_CODES` closed set, via an exhaustive `switch` the type checker rejects at compile time if a
  code is left unhandled (a `never`-typed fallthrough).
- **R4** For any reason record whose `code` is not one of the vendored `REASON_CODES` (a fabricated
  value, or a real one the mapping was never updated for after a future re-vendor),
  `mapReasonRecordToDesignMessage` SHALL throw rather than render a best-effort or placeholder string.
- **R5** `shaper_relation`'s nested `params.inner` reason SHALL itself be mapped through the catalog
  recursively — the composed message SHALL NOT embed the inner reason's raw vendored text.
- **R6** A test SHALL import the vendored module's own `REASON_CODES` (never a hand-copied list in the
  test itself) and assert every code maps to a real, non-empty catalogued message — so a future
  re-vendor that adds a code with no matching catalog entry fails this test even if, by some future
  refactor, the compile-time exhaustiveness check in R3 were weakened.
- **R7** A test SHALL construct a reason record with a code outside `REASON_CODES` and assert
  `mapReasonRecordToDesignMessage` throws (R4, exercised directly).
- **R8** Existing consumers of `evaluateReview`/`summarizeIndependence` (`gate.ts`'s
  `designEstablishmentGate`, `commands/design.ts`'s `runDesignStatus`) SHALL continue to work
  unmodified — this change is additive to `ReviewEvaluation.reasons`'s *content quality*, not its
  shape (`string[]`-compatible; `CatalogBackedDesignMessage` is a branded `string`) or its consumers'
  control flow.

## Gherkin scenarios

```gherkin
Feature: R46 — reason text composed entirely from catalogued messages

  Scenario: every vendored reason code known today maps to a catalog entry
    Given the vendored derive-independence.mjs's REASON_CODES (20 codes)
    When each code is rendered via mapReasonRecordToDesignMessage with a plausible sample record
    Then every one produces a non-empty string
    And none of them throws

  Scenario: a nested shaper-comparison reason is composed recursively from the catalog
    Given a "shaper_relation" record whose params.inner is a "same_provider_different_family" record
    When it is mapped to a design message
    Then the outer message embeds the INNER record's own catalogued rendering
    And the composed text is not the vendored module's raw formatReasonRecord() output

  Scenario: an unrecognized reason code fails closed
    Given a reason record whose code is not in REASON_CODES (e.g. a future re-vendor added a code
      this mapping was never updated for, or the input was corrupted)
    When it is mapped to a design message
    Then mapReasonRecordToDesignMessage throws
    And no placeholder-filled or partially-rendered string is returned

  Scenario: the vendored pin is re-verified after the re-vendor
    Given packages/core/src/vendor/derive-independence/UPSTREAM records commit
      36df11adfb361873abbc04ec864aa5a36f8e9d7e and a content hash
    When upstream-markers.test.ts's always-run content check runs
    Then the recorded hash matches the vendored file's actual bytes

  Scenario: existing gate/status behavior is unaffected
    Given a real design-options document with a mix of qualifying and non-qualifying reviews
    When lane design status and the design_establishment gate evaluate it
    Then the derived_status/qualifying/coverage/establishment outcomes are exactly what they were
      before this change
    And every review's reasons are now CatalogBackedDesignMessage[] instead of plain string[]
```

## Dependency and path cross-check

`allowed_paths` in `intent.yaml` covers every file this change touches:
`packages/core/src/vendor/derive-independence/**` (the vendored `.mjs`, hand-written `.d.mts`, and
`UPSTREAM` marker), `packages/core/src/design-independence.ts`, `packages/core/src/design-messages.ts`
(the new catalog entries), and `packages/core/test/**` (the new living-contract test plus the
necessary update to `pin-verify.test.ts`'s hardcoded pin constants, which is a test-only consequence
of R2, not a new capability). No file outside these paths is modified by the implementation.
